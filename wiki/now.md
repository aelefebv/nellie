## Recently shipped

- **🎉 mocap_marking optimization audit closed (3 PRs, ~48% on Markers.run() 3D)** (2026-05-11) — Audit of `nellie/segmentation/mocap_marking.py` shipped as 3 PRs into `dechao`: PR A — sparse cKDTree NMS in `_remove_close_peaks` (PRD #179, slices #182 + #183, ADR 0006). Replaces morphological max-filter with `scipy.spatial.cKDTree(coords).query_pairs(r, p=∞)` — Chebyshev metric preserves morphological semantics exactly. Drops `_remove_close_peaks_chunked` + `_nms_halo` (sparse memory is O(P), not O(N)). 3D `_remove_close_peaks` 9.3 ms → sub-ms (10×+ asymptotic on realistic frames). PR B — thread per-sigma LoG loop in `_local_max_peak` (PRD #184, slices #187 + #188, ADR 0007). `ThreadPoolExecutor` with `as_completed` — per-sigma reduction is provably ORDER-INDEPENDENT (final `peak_mask` is True iff voxel is local max for at least one sigma with positive log_resp; `best_resp` is internal state only), so no need to preserve original sigma order unlike PRD #173's writeback-serialization. Chunked path NOT threaded (would re-introduce memory pressure chunking bounds). 3D `_local_max_peak` 161 ms → 41 ms (3.9×). PR C — bundled micro-cleanups (#189): `gaussian_laplace(output=)` to skip astype copy + in-place clamp via `xp.maximum(..., out=)` + in-place XOR in `_distance_im` border + drop redundant `astype(bool, copy=False)` on already-bool. **Cumulative: 3D `Markers.run()` 494.8 ms → 255.8 ms (-48%)**, 3D `_remove_close_peaks` >10× speedup, 3D `_local_max_peak` 3.9× speedup. Test count: 45 → 56 mocap tests (16 sparse-NMS synthetic + 10 LoG-peak synthetic + 1 serial-vs-threaded equivalence). Two new ADRs in `wiki/decisions/` (0006, 0007). Wiki article `wiki/segmentation/mocap-marking.md` updated to reflect sparse cKDTree (reverses the prior "GPU-friendliness" framing — Markers is not MPS-onboarded and the CUDA path is unvalidated).

## Watch list

- **Tracking modules are unpinned.** Until the test rebuild reaches `nellie/tracking/`, claims like dense/sparse equivalence, `_log_hu` finiteness, and the hardcoded `1.0` cost cutoff have no automated guard. Treat changes there as un-regression-tested. (PRD #153's perf coverage gives wall-clock visibility on `voxel_reassignment` + `hu_tracking`, but not correctness — perf regressions become visible, semantic regressions don't.)
- **GPU/CUDA paths in the perf pass are untested.** All perf tests (filtering + the 7 added in PRD #153) run `device="cpu"`. The 4 onboarded stages also have MPS-marked variants (only exercised when `pytest -m mps` is run on a Mac); CUDA has zero coverage. The dispatcher's `bool(h_mask.all())` in filtering would force a D→H sync on GPU — pin this with a real GPU run before assuming the savings carry over.
- **Per-stage hot-path microbenchmarks are educated-guess.** PRD #153 added microbenchmarks for Label/Network/Hu/Markers/VoxelReassigner/Hierarchy chosen by reading the code, not by profiling. Treat the printed `[perf]` lines as scaffolding — when a future perf pass starts on one of these stages, the author should validate which kernel actually dominates before optimizing the picked hot-path. Filter's microbenchmarks are the exception — those came from a real perf pass and pin specific decisions.
